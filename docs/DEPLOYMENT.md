## 1. What you are deploying

Two independent pieces. The app works without the backend — the coach and food
search simply report themselves unavailable, which is a legitimate shippable
configuration.

```
┌──────────────────────────┐
│  iOS app  (CodeMagic)    │
│                          │
│  SwiftData ◄── HealthKit │   Health data never leaves the device.
│      │                   │   There is no networking in HealthKitService,
│      │                   │   and CI fails the build if any appears.
│      ▼                   │
│  AIContextEngine         │   Builds a capped, profile-scoped summary:
│  (≤30 readings)          │   30 readings, no profile ID, no name,
│      │                   │   no raw HealthKit samples, no device ID.
└──────┼───────────────────┘
       │  HTTPS
       ▼
┌──────────────────────────┐
│  Backend  (Railway)      │   Stateless. No database. Nothing at rest.
│                          │
│  /v1/coach ─► OpenRouter ─► model provider
│  /v1/food  ─► USDA FoodData Central
│                          │
│  API keys live here only │
└──────────────────────────┘
```

**Why no database.** Railway offers Postgres and it would be easy to add. The
app is local-first, so there is no user data to store, no accounts to
authenticate, and no sync to reconcile. Adding one would create a health-data
store that must be secured, backed up and reasoned about under GDPR/HIPAA — for
no feature.

**Why a gateway rather than calling a provider directly.** An API key shipped in
an `.ipa` can be extracted from it. Keys stay server-side. Using OpenRouter on
top of that means switching models is an environment variable rather than a code
change.

**What crosses the network.** Only the `BPContextSnapshot`: recent readings with
their categories, averages, medication names with adherence percentages,
lifestyle totals, and optionally step count and resting heart rate. No profile
identifier, no name, no HRV, no sleep detail, no weight, no device identifier.

## 3. Stage 1 — Push to GitHub

```bash
git init
git checkout -b bp-coach

git add -A
git commit -m "BP Coach: iOS app, backend gateway, CI and deployment config"
```

Create an empty **private** repo on GitHub — no README, no .gitignore, the
project already has both. Then:

```bash
git remote add origin https://github.com/<you>/bp-coach.git
git push -u origin bp-coach
```

### Checkpoint

Run this **before** pushing and read the output:

```bash
./scripts/security-check.sh
```

All twelve lines must say PASS. Then confirm nothing sensitive went up:

```bash
git ls-files | grep -E '\.env$|xcodeproj' || echo "clean"
```

The `.xcodeproj` is generated by XcodeGen in CI and is deliberately not
committed, so it cannot drift from `project.yml`.

## 4. Stage 2 — Get API keys

**USDA** — <https://fdc.nal.usda.gov/api-key-signup.html>. Email address, key
arrives immediately. Free, no card.

**OpenRouter** — <https://openrouter.ai/keys> → Create Key. Copy it now; the
console will not show it again. Add credit under **Settings → Credits**, or
requests return 402.

One gateway key reaches every model OpenRouter fronts, so trying a different
model later is an environment variable, not a new account.

### Checkpoint

Both keys in your password manager. Neither anywhere near the repo.

## 5. Stage 3 — Deploy the backend to Railway

Railway comes before CodeMagic for two reasons: the iOS build needs the backend
URL, and verifying an API with `curl` is far easier than discovering it is
broken from inside an iOS app.

1. railway.app → **New Project** → **Deploy from GitHub repo**
2. Authorise Railway, pick `bp-coach`
3. When the service appears: **Settings** → **Root Directory** → `backend`
4. Railway reads `railway.json` and builds from the `Dockerfile`

Then **Variables** → add:

```
OPENROUTER_API_KEY = sk-or-v1-...
OPENROUTER_MODEL   = anthropic/claude-sonnet-4.5
USDA_FDC_API_KEY   = your-usda-key
NODE_ENV           = production
```

> **Check the model slug.** Model IDs on OpenRouter change as models ship and
> retire. Confirm the exact string at <https://openrouter.ai/models> before
> deploying — a wrong slug produces a 400 that the app surfaces as "the AI
> request was rejected". `/ready` echoes the slug back so you can see what the
> server is actually using.

Leave `PORT` alone. Railway injects it, and setting it yourself breaks routing.

Then **Settings** → **Networking** → **Generate Domain**. You will get something
like `bp-coach-production-a1b2.up.railway.app`.

### Checkpoint

```bash
export API=https://<your-domain>.up.railway.app

curl -s $API/health
# {"status":"ok","uptimeSeconds":42}

curl -s $API/ready
# services should read "configured" for both coach and food
```

If `/ready` says `not configured`, a variable is misnamed or you did not
redeploy after adding it.

Now exercise the live integrations — this is the only point where they are
actually tested:

```bash
# Food search — should return items carrying sodium values
curl -s "$API/v1/food/search?q=tomato%20soup&limit=3" | jq

# Coach — should return a paragraph about the reading
curl -s -X POST $API/v1/coach \
  -H 'content-type: application/json' \
  -d '{
    "question": "What does this reading mean?",
    "guidelineName": "ACC/AHA 2017",
    "readings": [{
      "systolic": 128, "diastolic": 82, "pulse": 72,
      "recordedAt": "2026-08-17T07:38:00Z",
      "timeOfDay": "Morning", "source": "Manual", "category": "Elevated"
    }],
    "averages": [], "medications": [], "lifestyle": []
  }' | jq
```

**Do not proceed until both return real data.**

## 6. Stage 4 — Build the iOS app on CodeMagic

1. codemagic.io → **Add application** → connect GitHub → pick `bp-coach`
2. Choose **codemagic.yaml** as the configuration source, not the UI editor
3. **Environment variables** → add:

```
BPCOACH_API_BASE_URL = https://<your-domain>.up.railway.app
NOTIFY_EMAIL         = you@example.com
```

`BPCOACH_API_BASE_URL` is a public URL, not a secret — it is fine in a build
config. No trailing slash. Leaving it unset produces a valid build where the
coach and food search report themselves unavailable.

4. Start a build on branch `bp-coach`

The workflow runs: security sweep → environment capture → XcodeGen → build →
test → deployment-target check → PNG bundle check → invariant sweep → backend
tests.

### Expect this to fail the first time

The iOS code has never been compiled. A first build across ~7,400 lines almost
always surfaces errors. That is what this stage is for.

When it fails, **send the log** — specifically the lines starting with `error:`.
Do not start hand-editing Swift; the failures usually cluster and one fix often
clears a dozen.

While you are there, record two values the log prints into `CLAUDE.md`:

- Xcode and Swift versions (stages A1/A2)
- the XcodeGen version (stage A6) — then pin it in `codemagic.yaml`, where
  `XCODEGEN_VERSION` is deliberately empty rather than guessed

### Checkpoint

The log shows `** BUILD SUCCEEDED **` and `** TEST SUCCEEDED **`.

## 7. Stage 5 — Get it onto a device

Only after stage 4 is green.

**Change the bundle identifier first.** `project.yml` currently reads
`app.bpcoach.ios`. Replace it with your own reverse-DNS prefix and push, or App
Store Connect will reject it.

**TestFlight** needs the Apple Developer account:

1. App Store Connect → **Apps** → **+** → New App, bundle ID matching
   `project.yml`
2. CodeMagic → **Distribution** → **iOS code signing** → connect App Store
   Connect with an API key
3. Add a `publishing:` block to `codemagic.yaml` for App Store Connect

**Simulator only:** CodeMagic can produce a `.app` artifact, but running it needs
a Mac. Without one, TestFlight on your own iPhone is the shortest path to seeing
the app.

## 8. Reference

### Environment variables (Railway)

| Variable | Required | Notes |
|---|---|---|
| `OPENROUTER_API_KEY` | for the coach | Absent → `/v1/coach` returns 503 and the app shows "not set up" |
| `OPENROUTER_MODEL` | no | Slug from openrouter.ai/models. Defaults to `anthropic/claude-sonnet-4.5` |
| `APP_REFERER` | no | Sent as HTTP-Referer for OpenRouter attribution. No user data |
| `USDA_FDC_API_KEY` | for food search | Absent → `/v1/food/*` returns 503 |
| `CORS_ORIGINS` | no | Comma-separated browser origins. Empty is correct for native-only |
| `RATE_LIMIT_MAX` | no | Default 30 |
| `RATE_LIMIT_WINDOW_MINUTES` | no | Default 15 |
| `NODE_ENV` | no | Set to `production` |
| `PORT` | **no** | **Injected by Railway. Do not set** |

A missing key is not an error state. The endpoint reports itself unconfigured
and the app degrades to manual entry.

### Environment variables (CodeMagic)

| Variable | Notes |
|---|---|
| `BPCOACH_API_BASE_URL` | Railway URL, no trailing slash. Public, not a secret |
| `NOTIFY_EMAIL` | Build notifications |
| `XCODEGEN_VERSION` | Empty until you read the real version from stage A6 |

### Endpoints

| Method | Path | Purpose |
|---|---|---|
| GET | `/health` | Liveness. Dependency-free by design: if it called upstreams, a provider outage would make Railway restart a healthy container |
| GET | `/ready` | Which services are configured, plus the model slug. Booleans and slugs only, never key material |
| POST | `/v1/coach` | Validates, caps, calls OpenRouter, screens the output |
| GET | `/v1/food/search?q=&limit=` | USDA search. Results without sodium are dropped, never zero-filled |
| GET | `/v1/food/:id` | Single food by FDC ID |

## 9. Safety and security architecture

### Urgency is decided on-device

`SafetyEngine` is a pure function of the reading — no network call, no model, no
async. The AI never sees that decision path. This is defended in three places:

1. **Structurally** — the crisis path cannot reach a model
2. **In the prompt** — urgency assessment, diagnosis, medication changes and
   prediction are all forbidden
3. **In output screening** — `screenResponse` inspects generated text for
   emergency instructions, diagnoses and medication advice, substituting a fixed
   reply when it trips

The third layer exists because a model told not to say "call 911" will
occasionally say it anyway. In a blood pressure app that is the worst available
failure, so it is checked rather than trusted.

### Enforced invariants

`scripts/security-check.sh` runs locally and in CI:

- No API keys or `.env` in the repository
- iOS never calls a provider endpoint directly
- No networking in `HealthKitService`
- No raw HealthKit metrics or profile identifiers in the wire payload
- No clinical thresholds outside the guideline and safety engines
- Request bodies redacted in the backend logger
- Container runs unprivileged (`USER node`)
- Liveness probe has no upstream dependency
- Rate limiting registered

Backend logs carry method, route, status and duration — never bodies. Richer
logs would make debugging easier and would also put blood pressure history in a
log aggregator.

## 10. Ongoing operations

Every push to `bp-coach` triggers CI. Railway redeploys on pushes touching
`backend/`.

**Rotate a key** — change it in Railway Variables, redeploy, verify `/ready`.
Nothing in the app or the repo changes; that is the point of keeping keys
server-side.

**Change the model** — set `OPENROUTER_MODEL`, redeploy, check `/ready` echoes
the new slug. No code change, no app release.

**Roll back the backend** — Railway → Deployments → pick a previous one →
Redeploy.

## 11. Troubleshooting

| Symptom | Cause |
|---|---|
| Railway build fails immediately | Root directory not set to `backend` |
| `/health` 404s | Domain not generated, or still deploying |
| `/ready` says `not configured` | Variable misnamed, or no redeploy after adding it |
| Coach returns 503 | `OPENROUTER_API_KEY` missing, invalid, or out of credit |
| Coach returns 502 "request was rejected" | Bad `OPENROUTER_MODEL` slug — check `/ready` |
| Coach returns 402 upstream | No OpenRouter credit |
| Coach works in curl, not the app | `BPCOACH_API_BASE_URL` unset in CodeMagic, or has a trailing slash |
| Food search returns `[]` | Query under 2 characters, or no USDA result carried a sodium value |
| CodeMagic: "No .xcodeproj found" | XcodeGen stage failed — read the stage B1 log |
| CodeMagic: scheme not found | `project.yml` scheme renamed without updating `SCHEME_NAME` |
| Rate limited while testing | 30 requests / 15 min per IP. Raise `RATE_LIMIT_MAX` temporarily |

## 12. What is not done

Stated plainly so nothing above reads as more finished than it is.

- **The iOS app has never compiled.** Stage 4 is the first time it will.
- **No Railway deployment exists yet.** The configuration is written, not run.
- **Neither API integration has been exercised against a live upstream.** The
  backend suite covers them with stubbed responses; stage 3 is the real test.
- **The bundle identifier is a placeholder.** Change it before stage 5.
- **No App Store metadata, screenshots, or privacy nutrition label.** Those come
  in the App Store readiness pass.

**What has been verified:** backend typecheck clean, 40/40 backend tests
passing, 12/12 security checks passing. All run, not asserted.
